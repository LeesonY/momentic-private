## 已交付的用户操作

1. 管理员在首次登录、没有项目时创建项目，使用真实服务器
   返回的 ID 进入项目，不再使用默认虚构 ID。
2. 在“模型管理”页面选择已有平台模型，点击“授权给当前项目”。
   后端 `POST /api/v1/projects/{projectId}/model-profiles`
   执行管理员身份、项目权限和模型存在性校验，调用现有
   `ModelRepository.grant` 在 PostgreSQL 中创建项目范围授权。
   不返回凭据。
3. `GET /api/v1/projects/{projectId}/model-profiles` 返回当前
   项目已授权模型的安全元数据，并通过登录鉴权、项目作用域
   校验与数据库 RLS。其他项目的模型授权不会泄漏到本项目。
4. 管理员从已授权的模型中选择默认模型，点击“保存默认模型”；
   调用现有 `PATCH /api/v1/projects/{projectId}`，
   绑定 `expectedVersion` 进行乐观并发控制；只有服务端
   返回成功才刷新项目状态/选择器。
5. 冒烟首页只读取当前项目模型列表，不再把平台所有模型都
   作为可直接选择的运行配置。无授权模型时明确禁止启动并
   提示管理员前往授权；禁用模型不作为可用候选。
6. 在首页选择本次模型、输入完整 path/query 网址，提交
   `RunCreate.modelProfileId` 与 `Idempotency-Key`。API
   独立检查授权后冻结模型 ID/版本。

## 权限与安全边界

- 平台管理员且具备项目配置权限才可新增模型项目授权；
  普通成员和非项目成员不被授予写入权限。
- 只读取已获权限的项目模型集合；不可把全局模型列表
  的展示当作使用授权。
- 前端不复制模型密钥，也不改变 `non_submitting` 的 URL
  冒烟策略；未授权显式模型不回退到其他默认模型。
- 预置的模型 grant 逻辑与现有项目默认模型原子绑定逻辑
  继续复用，已审批业务基线和历史 T17–T39 账本不变。
- 平台级模型列表仍用于模型管理，普通已认证账号的全局列表
  可见性为现有产品行为；本阶段将实际运行可选范围限定为
  项目授权模型，不宣称已经审计全平台元数据可见性策略。

### 两个 Windows 测试夹具的已知问题与处理

原有 T06 API 测试先前在 Windows 临时文件 POSIX 权限校验处
阻塞。测试夹具仅在 Windows 使用本次独立生成的随机 KEK
构造**测试内存 Vault**；生产 `SecretVault.fromProtectedFile`
及权限策略没有任何修改。随后发现测试使用 Linux
`unzip` 验证离线 ZIP，Windows 下命令不存在；
夹具改为 PowerShell `Expand-Archive`，保留 manifest
与文件 SHA-256 对比。两次阻塞都不是产品业务 Bug。
